## 배경과 문제 정의

무료체험 고객 모두에게 같은 쿠폰과 안내를 보내면 비용만 늘고 정작 전환 가능성이 높은 고객은 놓치기 쉽다. 이 프로젝트는 체험 기간의 방문·체류·출입 패턴으로 전환 가능성을 순위화하고 우선순위에 따라 개인화 메일을 자동 발송하는 흐름까지 구축하는 것을 목표로 한다.

메일 발송 비용은 낮다. 대상을 다소 넓게 잡는 부담보다 전환할 고객을 놓치는 비용이 더 크다고 판단했다. 이 때문에 재현율(Recall)에 가중치를 둔 **F2 Score**를 주지표로 정했다.

## 분석 과정

| 단계 | 내용 |
|---|---|
| **1. 데이터 전처리** | 신청·출입·방문·결제·지점 5개 테이블 정제, 자정을 넘긴 연속 체류 등 기록 구조 점검 |
| **2. 파생 변수 설계** | 체류시간·방문일수·출입횟수·지점 등 행동 변수 10종 생성 |
| **3. 사전 실험** | 미방문자 제외, 클래스 불균형 보정, 요일 변수 포함 여부를 직접 비교해 전처리 방침 결정 |
| **4. 모델 비교 · 튜닝** | 5개 모델을 동일 조건으로 비교, Optuna로 F2 기준 튜닝 |
| **5. 해석 · 개인화** | SHAP으로 고객별 기여 변수를 뽑아 메일 문구에 자동 매핑 |
| **6. 운영 연결** | Streamlit 예측 대시보드 → n8n 자동 발송 파이프라인 |

## 주요 발견

### 1. 미방문자는 모델이 가려낼 근거가 없다

체험 신청 후 한 번도 방문하지 않은 유저(약 37%)는 요일 외 모든 행동 변수가 0이거나 비어 있다. 모델 학습에서는 이들을 제외했고 운영에서는 평균 전환율을 적용하는 별도 규칙으로 처리했다.

### 2. 알고리즘보다 신호의 한계가 크다

| 모델 | F2 | AUC | Recall | Precision |
|---|---|---|---|---|
| Decision Tree | 0.615 | 0.593 | 0.681 | 0.442 |
| Logistic | 0.577 | 0.625 | 0.604 | 0.490 |
| **XGBoost ★** | **0.560** | **0.616** | **0.585** | **0.480** |
| CatBoost | 0.535 | 0.619 | 0.550 | 0.476 |
| LightGBM | 0.501 | 0.602 | 0.507 | 0.476 |

*튜닝 전 기본 설정 · 클래스 불균형 보정 적용 · F2 내림차순*

- 5개 모델의 AUC는 0.59~0.63에 모였다. 알고리즘의 우열보다 데이터 신호 자체의 한계가 크다고 판단했다.
- F2 1위인 Decision Tree는 Precision 0.442로 기저 전환율 대비 **리프트 1.14배**에 그친다. 전환 대상을 넓게 잡아 얻은 Recall이라 선별 타겟팅에는 맞지 않았다.
- Logistic(0.577)과 XGBoost(튜닝 후 0.579)의 성능은 대등했다. 최종 산출물에서는 SHAP 기여 변수를 개인화 문구로 바꾸어야 했다. 고객별 기여 변수를 반영할 수 있는 트리 기반 XGBoost를 채택했다.

### 3. 고객별 행동 신호를 서로 다른 문장으로 바꾼다

각 고객에게 SHAP 기여도가 가장 큰 행동 변수 1개를 골라 메일 제목·본문에 자동으로 넣는다. 같은 캠페인이어도 고객별 메일 문구가 달라진다.

| 변수 | 경향 | 개인화 문구 |
|---|---|---|
| `last_visit_to_end_gap` | 마지막 방문이 종료일과 멀수록 전환 확률 ↓ | 체험 마지막 날까지 꾸준히 나와주셨더라고요. |
| `visit_days` | 방문일수가 많을수록 ↑ | 짧은 체험 기간에도 여러 번 찾아주셨어요. |
| `stay_total_sec` | 총 체류시간이 길수록 ↑ | 오실 때마다 오래 집중해서 일하시더라고요. |
| `n_access_events` | 출입 횟수가 많을수록 ↑ | 체험 기간 동안 자주 방문하셨네요. |
| `n_sites_visited` | 방문 지점이 많을수록 ↑ | 여러 지점을 두루 둘러보셨어요. |

*총 체류시간은 평균 체류시간 × 방문일수이므로 세 변수 사이에 종속 관계가 있어 SHAP 방향이 달라진다. 방향이 안정적인 변수만 문구 매핑에 사용했다.*

## n8n 자동 발송

```
최신 타겟 CSV 불러오기 → 세그먼트 필터링 → 중복 발송 제외 → 개인화 메일 발송 → 발송 로그 기록
```

| 브랜치 | 역할 |
|---|---|
| **A · Google Drive** | Streamlit에서 만든 최신 타겟 CSV를 가져와 '높음' 세그먼트만 필터링 |
| **B · Google Sheets** | 기존 발송 로그를 불러와 이메일 기준으로 비교 |
| **Compare → 발송** | A에만 있는 고객(미발송)에게만 SMTP로 메일 발송 후 로그 시트에 기록 |

평일 오전 10시에 실행한다. 발송 로그를 대조해 같은 고객에게는 중복 발송하지 않는다. 워크플로는 [`n8n_workflow.json`](n8n_workflow.json)으로 가져올 수 있다. 계정 정보는 제거되어 있으므로 본인의 Google·SMTP 계정을 다시 연결해야 한다.
